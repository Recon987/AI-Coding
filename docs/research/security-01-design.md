# 저장·백업 암호화 위협 모델과 설계안 (TASK-SECURITY-01 1단계)

작성 2026-10-20, Claude(구현 담당). 제품 코드는 바꾸지 않았다. **2026-10-20 사용자 결정(10장)으로 권장안 D를 채택**했고 8장대로 구현 카드를 나눴다.

## 1. 왜 지금 필요한가

업무 자료와 모든 사본이 평문 JSON이다. 지금은 가상 자료와 개인 업무 메모 수준이라 괜찮지만, 다음을 넣으려면 먼저 보호가 필요하다(도메인 검토 D6·D9, 프로젝트 검토 39행).

- 전화메모의 민원인 이름·연락처(지금도 입력 가능)
- 단속 기록의 인적사항(현재 필드 없음 — 암호화 전에는 만들지 않기로 함)
- 직원 이름·근무표(사무소 현황)

## 3. 위협 모델

**지킬 것**: 민원인 연락처, 직원 이름·근무, 업무 메모·인수인계 내용, AX 사업 예산 메모.

| ID | 상황 | 지금 | 앱 암호화로 막을 수 있나 |
| --- | --- | --- | --- |
| T1 | PC·디스크 분실·도난, 폐기 디스크 | 디스크를 다른 PC에 붙이면 그대로 읽힘 | **예**(키가 그 Windows 계정에 묶이면). BitLocker가 켜져 있으면 이미 대부분 막힘 |
| T2 | 공용 PC의 다른 Windows 계정 | 일반 계정은 NTFS로 막히나 관리자 계정은 읽음 | **예**(DPAPI 키는 그 사용자만 풀 수 있음, 관리자도 사용자 암호 없이는 어려움) |
| T3 | 백업 파일을 USB·메일로 옮기다 분실 | 그대로 읽힘 | **예**(백업 전용 암호) |
| T4 | 로밍 프로필·OneDrive 동기화로 `%APPDATA%`가 서버에 복사 | 서버·다른 PC에 평문 사본 | **예**(동기화되는 것이 봉한 파일) |
| T5 | 내보낸 TXT/CSV/보고서·클립보드·알림 | 평문 | **아니오** — 사람이 읽으려고 만드는 것. 안내·선택 사항으로 줄인다 |
| T6 | 같은 Windows 계정으로 도는 악성코드, 자리 비운 사이 조작 | 다 읽힘 | **아니오** — DPAPI도 같은 계정 프로그램에는 열림. 화면 잠금·백신 정책 몫 |
| T7 | 실행 중 메모리·스왑 분석 | — | 범위 밖 |

T6을 막는다고 주장하지 않는다. 앱 안 PIN 화면만 추가하는 것은 T1~T4를 막지 못하므로 채택하지 않는다(참고 앱의 기기 ID 키·4자리 PIN 방식은 오프라인 대입에 약해 쓰지 않음, 프로젝트 검토 13행).

## 4. 선택지

| 안 | 내용 | 사용자 부담 | 막는 위협 | 큰 위험 |
| --- | --- | --- | --- | --- |
| A | 앱은 그대로, 기관 BitLocker·계정 정책에 맡김 | 없음 | T1(BitLocker 켜진 경우) | T2·T3·T4 그대로 |
| B | 무작위 데이터 키로 저장 파일 AES-256-GCM, 데이터 키는 Electron `safeStorage`(Windows DPAPI, 현재 사용자)로 감쌈 | 없음(자동) | T1·T2·T4 | Windows 재설치·계정 재생성·프로필 손상·다른 PC 이동 때 **키를 잃어 자료를 못 엶** → 복구 수단 필수 |
| C | 매번 암호/PIN 입력, 암호에서 키 유도 | 실행마다 입력 | T1·T2·T4 | 암호 잊으면 복구 불가. 짧은 PIN은 대입에 약함 |
| **D (권장)** | **B + 복구 키 + 암호 백업**: 저장은 B로 자동, 같은 데이터 키를 종이 복구 키로도 감싸 둠, 백업 파일은 사용자가 정한 백업 암호(scrypt)로 따로 봉함 | 처음 한 번 복구 키 보관, 백업 때 암호 입력 | T1·T2·T3·T4 | 복구 키와 백업 암호를 둘 다 잃으면 다른 PC에서 못 엶(같은 PC·계정에서는 계속 열림) |

**권장은 D**다. 평소 사용 흐름은 지금과 같고(입력 없음), PC 밖으로 나가는 백업만 암호를 묻는다.

## 5. 권장안 D의 동작

- **데이터 키**: 처음 켤 때 무작위 256비트. `safeStorage.encryptString`으로 감싼 값과, 복구 키로 감싼 값을 `workdesk.key.json`에 함께 저장. 데이터 키 자체는 디스크에 평문으로 두지 않는다.
- **복구 키**: 처음 켤 때 한 번 보여 주는 무작위 문자열(예: 4자리씩 6묶음, 120비트 이상). 인쇄·종이 보관 안내. 앱은 다시 보여 주지 않는다(재발급은 현재 키로 새로 만드는 방식).
- **저장 파일 형식(봉투)**: `{"version":3,"minReader":3,"sealed":{"alg":"AES-256-GCM","keyId":…,"iv":…,"tag":…,"data":…}}`. 안쪽 평문은 지금의 v3 자료 그대로라 **자료 스키마는 바뀌지 않는다**. 암호화는 저장 계층(store.cjs)에서만 한다.
  - `minReader: 3`을 쓰면 SCHEMA-01 이후의 구버전 앱은 "새 버전 자료"로 보고 **파일을 바꾸지 않고** 멈춘다(이미 검증된 경로, `isNewerData`). SCHEMA-01 이전 앱은 손상으로 보고 바이트 사본을 남긴다(삭제는 없음).
- **모든 사본 봉함**: last-good, 복원 보호본, 개편 전 보호본, v1/v2 전환 사본, 손상 사본(봉한 파일이면 그대로 바이트 복사)까지 같은 봉투를 쓴다. 임시 `.tmp`도 봉한 바이트만 쓴다.
- **백업**: 내보낼 때 백업 암호를 두 번 입력 → scrypt(N=2^17, r=8, p=1)로 키 유도 → AES-256-GCM. 복원할 때는 암호를 묻는다. 평문 백업(기존 형식) 복원은 계속 지원(읽기만).
- **전환(처음 한 번)**: 평문 주 파일을 먼저 봉한 보호본(`.pre-encryption-backup`)으로 만들고, 주 파일·모든 평문 사본을 봉투로 바꾼 뒤 평문 사본을 지운다. 실패하면 원본 평문을 그대로 둔다(지금의 원자적 저장 계약 유지).
  - **한계**: SSD·저널링 때문에 지운 평문이 디스크에 남을 수 있다. 앱이 완전 삭제를 보장할 수 없으므로 BitLocker 병행을 권장 문구로 안내한다.
- **크기 한도**: 20MB는 평문 기준으로 유지하고, 봉한 파일(base64)은 약 1.34배까지 허용한다.

## 6. 성능 측정 (가상 자료, `node scripts/security-bench.cjs`)

Linux Node 22, Xeon 2.8GHz. 한글 메모로 채운 v3 형태 JSON.

| 크기 | AES-256-GCM 봉함(중앙값) | 열기(중앙값) | 1바이트 변조 |
| --- | --- | --- | --- |
| 1MB | 1.9ms | 1.7ms | 거부 |
| 5MB | 7.3ms | 7.3ms | 거부 |
| 20MB(한도) | 175ms(최대 288ms) | 15ms | 거부 |

| 백업 암호 키 유도 scrypt | 메모리 | 시간(중앙값) |
| --- | --- | --- |
| N=2^15 | 32MB | 95ms |
| N=2^16 | 64MB | 184ms |
| N=2^17(권장) | 128MB | 427ms |

봉함·열기 비용은 현재 저장(fsync 포함)에 비해 작다. 백업 암호 유도 0.4초는 백업·복원 때 한 번이라 받아들일 만하다. 기관 PC(더 느린 CPU)에서 다시 잰다.

`safeStorage` 확인: 이 Linux 클라우드 환경은 키링이 없어 `isEncryptionAvailable() = false`(backend `basic_text`)다. Windows에서는 DPAPI를 쓰므로 사용 가능할 것으로 보지만 **추측이므로 구현 단계에서 Windows Actions와 기관 PC에서 확인**한다. 사용할 수 없는 환경에서는 암호화를 켜지 않고 이유를 보여 준다(조용히 평문으로 저장하지 않음).

## 7. 그대로 평문인 것(T5)과 줄이는 방법

- 내보내기(브리핑·양식·보고서)·클립보드: 사람이 읽으려고 만드는 것이라 암호화하지 않는다. 저장 대화상자 옆에 "이 파일은 암호화되지 않습니다" 안내를 둔다.
- OS 알림: 제목이 알림 센터에 남는다. 선택 사항으로 "알림에 제목 숨기기"(예: "일정 알림 1건")를 둘 수 있다.

## 8. 구현을 나눌 카드(승인 뒤)

1. SECURITY-02 저장 봉투·키 관리(store.cjs, safeStorage, 복구 키 발급·입력 화면), 구버전 혼용 검사
2. SECURITY-03 백업 암호(내보내기·복원 대화상자, scrypt), 평문 백업 읽기 유지
3. SECURITY-04 평문→봉함 전환·평문 사본 정리·실패 시 원본 보존, 성능·Windows 실측
4. (선택) SECURITY-05 내보내기 안내·알림 제목 숨김

각 카드는 가상 자료로 검증하고, 키 분실·복구 키 입력·암호 틀림·변조·디스크 가득 참·전환 중 중단을 실제 앱 검사로 확인한다.

## 9. 결정이 필요한 것

1. **보호 방식**: D(권장) / A(기관 BitLocker에 맡김, 앱 변경 없음) / B(복구 키 없이 자동만) / C(매번 암호)
2. **복구 키**: 발급(권장, 종이 보관) / 발급 안 함(백업 암호만이 다른 PC 복구 수단)
3. **백업 암호**: 백업할 때마다 입력(권장) / 한 번 정해 저장(편하지만 같은 PC에서는 보호가 약해짐)
4. **알림 제목 숨김**: 선택 기능으로 둠 / 두지 않음
5. **기관 PC 사정(알려 주시면 설계에 반영)**: BitLocker 사용 여부, 로밍 프로필·OneDrive로 `%APPDATA%` 동기화 여부, 한 PC를 여러 사람이 쓰는지

## 10. 사용자 결정 (2026-10-20)

| 항목 | 결정 |
| --- | --- |
| 보호 방식 | **D**: DPAPI 자동 암호화 + 복구 키 + 백업 암호 |
| 복구 키 | 발급(D에 포함) — 처음 한 번 보여 주고 종이 보관 안내 |
