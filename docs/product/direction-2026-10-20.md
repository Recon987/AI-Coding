# 국립공원공단 업무 수첩 — 제품 방향 재점검

2026-10-20 / 작성 Codex / 상태: 사용자 의도를 반영한 검토안, Claude·Gemini 합의 전.
기준: main ea3105e 및 검증 기록960d2fb. 원격 Claude4c4f521은 SECURITY-03 진행 중이며 그 코드는 이번 검토에 통합하지 않았다.

## 1. 제품의 중심

**공단 직원이 자기 업무·사업·회의·자료·성과를 한곳에 축적하고, 직무에 맞는 도구를 더하며, 기관 연계가 준비되면 같은 업무 맥락에서 협업하는 데스크톱 업무 허브.**

사용자 확인: 사업/업무/자료를 연결하는 것, 반복 보고 시간을 줄이는 것, 인계·공유 누락을 줄이는 것을 모두 포함해야 범용적이다. 개인 단독 사용으로도 가치가 있어야 하며, 팀 기능은 그 위에 확장한다. 제품의 공식 명칭 확정은 별도다.

## 3. 범용 코어와 전문 모듈

| 층 | 사용자가 받는 기능 | 공통 계약 |
| --- | --- | --- |
| 내 업무 | 빠른 기록, 할 일, 오늘/이번 주, 회의·전화 후속 처리, 검색 | 같은 기록을 목록·보드·달력에서 보고 완료 상태를 공유 |
| 사업·업무 공간 | 목표·단계·작업·회의/결정·기한·근거 자료·주간 실적 | 관련 기록 ID로 연결, 원본 복제 없이 조회/보고에 재사용 |
| 전문 모듈 | AX·시설/용역·자원보전 조사·탐방안전/순찰 등의 필드·계산·양식 | 공통 사업/업무를 사용하고 전문 부분만 확장 |
| 기관 연계 | 조직/담당/일정 조회 → 공유 업무/댓글/활동 이력 → 필요하면 메시지 연계 | 계정·권한·외부ID·변경 버전·충돌/오류를 다루는 어댑터 |

모든 짧은 할 일을 사업에 강제로 넣지 않는다. 사람별/사업별/기간별 보기는 같은 원본의 표현이다. 정해진 업무용 템플릿부터 제공하고 임의 스크립트 플러그인 실행이나 만능 사용자 DB 편집기를 첫 목표로 삼지 않는다.

예시(업무 가설이며 공식 절차 아님):
- 시설 담당: 정비 사업 생성 → 현장 확인/회의 메모 → 후속 작업·마감 → 근거 파일 연결 → 추진 실적 초안.
- 자원보전 담당: 조사 계획 → 조사 기록·사진/자료 연결 → 미해결 항목 → 결과 정리·인계.
- AX 담당: 실증 사업 → 계약/마일스톤·협의 기록 → 산출물/코드 참조 → 주간 실적.
- 행정 담당: 요청 접수 → 여러 부서 자료 취합 작업 → 검토/제출 기한 → 회신·보고 근거 보존.

기능의 확장 효과는 이 네 흐름을 같은 코어로 수행하는 데서 나온다. 각 직무마다 별도 앱을 만드는 방식은 피한다.

## 4. 다음 체감 변화가 큰 개발 묶음

### A. 먼저 보여 줄 제품 경험: ‘사업 하나를 끝까지 진행하는 업무 공간’

권고 우선순위이며 구현 착수/전체 우선순위 확정은 아니다. 새로운 작은 보완 카드를 계속 잇기 전에 다음 세 화면의 연결된 시제품을 공동 검토한다.
1. **오늘의 업무**: 사업을 가로질러 오늘 기한·진행 중·회신 대기를 보고 빠르게 기록/작업 등록.
2. **사업 공간**: 개요, 작업 목록/보드, 회의·결정, 자료, 활동, 실적. 세부 화면은 점진적으로 추가한다.
3. **정리·보고**: 같은 기간의 완료 작업·결정·남은 쟁점에서 주간 보고/인계 초안. 근거 기록으로 돌아갈 수 있음.

핵심 데모: ‘전화/회의 메모에서 후속 작업을 만들고 → 사업에 연결 → 기한을 오늘 화면/달력에 반영 → 완료 → 실적 초안에 근거와 함께 반영’. 같은 내용을 화면마다 다시 입력하지 않는다. 일반 업무 하나를 먼저 완주하고 AX/순찰 연결을 붙인다.

### B. 전문성·축적: 직무 템플릿과 데스크톱 유틸리티

공통 업무 공간을 사용하는 전문 모듈 2종에서 재사용을 확인한다. AX의 기존 필드·순찰 원본을 임의로 일괄 변환하지 않고 참조부터 설계한다. 근거 자료 링크·인계 묶음·보고 양식·전역 빠른 등록·명령 검색을 실제 사용 순서로 추가한다. 대량 파일명 변경·임의 코드 실행 등의 유틸리티는 미리보기/되돌리기 계약과 별도 수요가 있어야 채택한다.

### C. 기관 연계와 협업

첫 결과물은 실제 API로 착각할 수 없는 가상 어댑터와 계약 문서다. 조직·사용자·담당 업무/일정의 승인된 읽기 전용 연결을 먼저 확인한다. 공동 편집/업무 배정/댓글/메시지는 사용자 식별·권한·서버 저장·동기화·충돌·감사·알림 전달이 확인된 뒤 단계적으로 제공한다. 내부 API가 있다는 사실만으로 이 기능들이 자동으로 생기지는 않는다. 기존 기관 메신저 API가 있으면 연계도 비교한다.

개인 오프라인 모드는 계속 유효하다. 기관 연결 모드는 별도 운영/네트워크 계약으로 정의한다. 이번 검토에서는 AGENTS.md의 오프라인 실행 규칙을 바꾸거나 API 접속을 하지 않았다.

## 8. 세 에이전트 협업·토큰 사용 제안

1. 총괄 Claude: 공통 제품 목표/단계/결정 목록 한 벌을 관리하고 다른 제안을 중복 카드로 만들지 않는다. 이번에 진행 중인 보안 작업은 현재 체크포인트로 보존한다.
2. Gemini: 네 직무 시나리오에서 빠진 범용 흐름과 화면 동선/레퍼런스를 비평한다. 원문 전체를 다시 쓰는 대신 반례·근거·결정할 쟁점으로 응답한다.
3. Codex: 연결 모델/저장·모듈 계약·성능 측정·실행 가능한 기능 묶음 구현과 독립 검증을 담당한다. 구현자와 최종 검증자는 분리한다.
4. 한 과제의 배경을 세 모델이 각각 조사하지 않는다. 공유 브리프+기준SHA+관련diff/인터페이스+시나리오+검증 결과를 전달한다. 전체 handoff/로그는 필요한 부분만 읽는다.
5. 검토는 단계 경계에서 한 번, 쟁점이 남으면 해당 쟁점만 후속 검토한다. 일상 수정마다3모델회의/화면150개/전체스위트를 반복하지 않는다. 자료 손실·시작 불가 P0/P1은 즉시 처리하고 비차단 보완은 같은 출시 묶음으로 모은다.
6. 짧은 인계는 목표·해시·변경계약·결과·결정할점5항목, 발견은최대5개를기본으로한다(초과핵심발견은생략하지않음). 토큰/비용절감률은실측전단정하지않는다.
