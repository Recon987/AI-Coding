# 검토 관점

개선 루프의 ① 검토 단계에서 쓰는 관점이다. 관점마다 1~5점으로 평가하되 **점수보다 근거가 우선**이다. 근거 없는 점수는 기록하지 않는다. 점수는 같은 관점의 이전 주기와 비교하는 용도이며 제품 완성도를 증명하지 않는다.

| 점수 | 의미 |
| --- | --- |
| 1 | 해당 관점에서 쓸 수 없다 |
| 2 | 핵심 흐름이 막히거나 크게 불편하다 |
| 3 | 쓸 수 있지만 매번 우회·추측이 필요하다 |
| 4 | 대부분 자연스럽고 남은 문제는 국소적이다 |
| 5 | 비교 대상 레퍼런스와 견줄 만하다 |

## A. 도메인 적합성 — 국립공원공단 업무를 담고 있는가

- 실제 직무(자원보전, 탐방 안전, 재난·산불, 불법행위 단속, 탐방로·시설 관리, 대피소·야영장, 행정·서무)별로 하루·한 주의 업무 흐름이 앱 안에서 이어지는가?
- 화면 용어가 현장에서 쓰는 말(예: 순찰 구간, 통제, 기상특보, 단속, 시설 점검)과 일치하는가?
- 기관이 이미 쓰는 서식·보고 체계와 충돌하지 않고, 개인 기록 도구로서의 한계를 정확히 말하는가?
- 근거: 공개된 공단 자료, 법령·지침, 사용자가 제공한 서식. **추측한 업무 규칙은 "가설"로 표시한다.**

## B. 사용 흐름(UX) — 처음 쓰는 사람이 바로 쓰는가

- 출근 → 확인 → 기록 → 인계 → 퇴근의 주요 과업을 몇 번의 조작으로 끝내는가? (과업별 클릭 수·화면 이동 수 측정)
- 현장 복귀 직후처럼 시간이 없을 때 빠르게 기록할 수 있는가?
- 오류·빈 상태·저장 실패에서 무엇을 해야 하는지 알려주는가?
- 키보드만으로 쓸 수 있는가? 접근성 이름이 맞는가?

## C. 시각 디자인 — 정보가 한눈에 들어오는가

- 비교 대상(업무용 데스크톱 앱·일정/할 일 도구·현장 기록 앱)과 나란히 놓았을 때 위계·밀도·일관성이 어떤가?
- 색이 의미를 일관되게 쓰는가(위험/주의/완료)? 색만으로 의미를 전달하지 않는가?
- 1280×800, 960×680, 125% 배율에서 깨지지 않는가? (`npm run review:ui` 측정 사용)

## D. 자료 안전 — 기록을 잃지 않는가

- 손상 파일·정전·디스크 부족·잘못된 백업에서 복구 경로가 있는가?
- 형식 전환·복원 전에 원본이 보존되는가? 평문 저장의 위험을 사용자에게 알리는가?

## E. 품질·성능 — 오래 써도 안정적인가

- 한도(20MB·10,000건) 근처 자료로 시작·검색·저장 시간이 허용 범위인가?
- 테스트가 실제 사용 경로를 덮는가? 테스트 없이 바뀐 공유 로직이 있는가?

## F. 운영·배포 — 기관 PC에 실제로 깔 수 있는가

- 폐쇄망 설치·업데이트 절차, 서명 부재 경고, 관리자 권한 필요 여부가 문서화되어 있는가?
- 실기기 검증(토스트·절전·스크린리더·고배율) 결과가 Actions 결과와 구분되어 있는가?

## 검토 문서 양식

`docs/reviews/<YYYY-MM-DD>-<관점>.md`:

```markdown
# <관점> 검토 — <날짜>
- 검토자: <에이전트> / 기준 커밋: <해시>
- 점수: n/5 (이전: m/5)

## 발견
| # | 심각도(P0~P3) | 내용 | 근거(파일:줄, 화면, 출처) | 제안 |

## 레퍼런스 (해당 시)
| 대상 | 참고할 점 | 그대로 가져오면 안 되는 점 |
```
