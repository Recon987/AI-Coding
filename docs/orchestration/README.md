# 에이전트 운영 체계

Codex·Gemini·Claude가 같은 저장소를 번갈아 수정해도 **누가 무엇을 어디까지 했는지** 잃지 않게 하는 규칙이다. [AGENTS.md](../../AGENTS.md)의 핵심 원칙(오프라인·격리·자료 보존)은 그대로 유지하고, 이 문서는 **작업을 나누고 넘기는 방법**만 정한다.

## 1. 해결하려는 문제

| 이전 방식 | 문제 | 바꾼 방식 |
| --- | --- | --- |
| 모든 에이전트가 `main`에 직접 커밋 | 같은 파일을 동시에 고치고, 웹 업로드 커밋이 검증 없이 들어감 | 과제마다 `task/<ID>` 브랜치, 검증 후 `main` 병합 |
| `docs/handoff.md` 한 문서에 상태를 덮어씀 | 이전 상태가 사라지고 문서가 길어짐 | 과제 카드(`docs/tasks/<ID>.md`) 하나에 그 과제의 모든 상태 |
| Step이 끝나야 커밋 | 시간 한도에 걸리면 작업 전체가 사라짐 | 세부 단계마다 체크포인트 커밋·푸시 |
| 구현자가 스스로 완료 판정 | 같은 시각으로 같은 결함을 놓침 | 구현자 ≠ 검증자 |
| 역할이 대화마다 달라짐 | "이번엔 누가 뭘 하지?"를 매번 정함 | 역할 고정, 배정은 카드에 기록 |

## 2. 역할

역할은 에이전트와 분리한다. 아래 **기본 배정**은 사용자가 언제든 바꿀 수 있고, 바꾸면 이 표를 수정한다.

| 역할 | 하는 일 | 하지 않는 일 | 기본 배정 |
| --- | --- | --- | --- |
| **제품 책임자** | 우선순위 승인, 실제 업무 서식·용어 제공, 실기기 확인, 범위 결정 | — | 사용자 |
| **총괄** (orchestrator) | 보드 관리, 검토 결과를 과제 카드로 분해, 의존성·순서 제안, `main` 병합, 인계 정리 | 승인 없이 우선순위 확정 | Claude |
| **구현** (builder) | 카드 1개를 브랜치에서 구현, 체크포인트 기록 | 카드 범위 밖 수정, 자기 결과 최종 승인 | Codex (보조: Claude) |
| **검증** (verifier) | 완료 조건 대조, 테스트 재실행, 코드 리뷰, 화면 확인 | 직접 기능 추가(발견은 카드로) | 구현자가 아닌 쪽 (Codex↔Claude) |
| **도메인 조사** (domain) | 국립공원공단 업무·규정·서식 조사, 요구사항 정리 | 근거 없는 업무 규칙 단정 | Gemini |
| **디자인 검토** (design) | 유사 앱·시스템 레퍼런스 조사, 화면 비평, 개선안 | 코드 직접 수정 | Gemini (화면 캡처·측정: Claude) |

**Gemini가 git을 쓰지 않는 경우**(웹에서 결과를 받아 업로드하는 경우): Gemini의 결과물은 문서(`docs/research/`, `docs/reviews/`)로만 받는다. 코드 변경이 포함되면 git을 쓰는 에이전트가 해당 카드의 브랜치에 반영하고 테스트한 뒤 커밋한다. **GitHub 웹 업로드로 `main`에 직접 올리지 않는다.**

## 3. 과제 카드

모든 작업은 `docs/tasks/<ID>.md` 카드에서 시작하고 끝난다. 양식은 [TEMPLATE.md](../tasks/TEMPLATE.md). 상단 머리말 필드:

| 필드 | 값 |
| --- | --- |
| `id` | 파일명과 같음. 예: `TASK-DATA-01` |
| `status` | `backlog` → `ready` → `in-progress` → `review` → `done` (또는 `blocked`) |
| `role` | 주 역할: `builder` / `domain` / `design` / `orchestrator` / `verifier` |
| `owner` | 지금 맡은 에이전트: `codex` / `gemini` / `claude` / `user` / `none` |
| `verifier` | 검증할 에이전트. `owner`와 달라야 한다 |
| `branch` | `task/<ID 소문자>`. 문서만 다루는 과제도 브랜치를 쓴다. 클라우드 세션이 지정 브랜치(`claude/…`, `codex/…`)만 허용하면 그 이름을 적는다 |
| `depends` | 먼저 끝나야 하는 카드 ID (쉼표 구분, 없으면 비움) |
| `priority` | `P0`(자료 손실·실행 불가) / `P1`(핵심 업무 흐름) / `P2`(개선) / `P3`(아이디어) |
| `updated` | 마지막 수정일 `YYYY-MM-DD` |

`npm run board`가 카드를 읽어 현황판을 출력하고, `npm test`가 카드 규칙(필드·상태·담당·의존성)을 검사한다. 규칙을 어긴 카드가 있으면 테스트가 실패한다.

## 4. 작업 순서 (한 과제)

1. **시작**: `git fetch` → `npm run board` → 내 이름의 `in-progress`가 있으면 그 카드의 **재개 위치**부터 이어서 한다. 없으면 `ready` 중 의존성이 끝난 가장 높은 우선순위를 고른다.
2. **선점**: 카드의 `status: in-progress`, `owner`, `branch`, `updated`를 고치고 `task/<id>` 브랜치에 커밋·푸시한다. 푸시가 성공해야 선점이 성립한다. 원격에 같은 브랜치가 이미 있으면 그 브랜치를 이어받는다(새로 만들지 않는다).
3. **체크포인트**: 카드의 진행 단계 하나를 끝낼 때마다
   - 체크박스를 표시하고 **재개 위치**를 "다음에 할 정확한 일 + 관련 파일"로 고친다.
   - 테스트 상태를 사실대로 적는다(통과 / 실패 n건과 이유 / 미실행).
   - `wip(<ID>): <단계>` 메시지로 커밋하고 즉시 푸시한다. 체크포인트 커밋은 테스트 실패 상태여도 된다. 단 카드에 실패를 적는다.
4. **검증 요청**: 완료 조건을 모두 충족하고 `npm test`·`npm run test:desktop`이 통과하면 `status: review`로 바꾸고 푸시한다.
5. **검증**: `verifier`가 브랜치를 받아 완료 조건을 하나씩 대조하고 테스트를 직접 실행한다. 결과를 카드의 **검증 기록**에 적는다. 문제가 있으면 `in-progress`로 돌려보내고 이유를 적는다.
6. **병합**: 검증이 통과하면 총괄이 `main`에 병합(merge commit, 강제 푸시 금지)하고 카드를 `done`으로 바꾼다. Windows Actions는 `main` 푸시와 PR에서 실행된다.

## 5. 시간 한도·중단 대비

- **15~20분마다 또는 세부 단계 하나마다** 체크포인트를 푸시한다. 푸시되지 않은 작업은 없는 것으로 본다.
- 한도가 가까우면 새 단계를 시작하지 말고 현재 상태를 카드에 적고 푸시한다.
- 다음 에이전트는 대화 내용이 아니라 **카드의 재개 위치와 브랜치**만 보고 이어받을 수 있어야 한다. 카드에 "앞에서 말한 대로" 같은 대화 의존 표현을 쓰지 않는다.
- 카드 하나는 한 세션(대략 1~2시간)에 끝날 크기로 자른다. 진행 단계가 6개를 넘으면 카드를 나눈다.
- 다른 에이전트의 `in-progress` 카드는 건드리지 않는다. `updated`가 3일 이상 지나고 푸시가 없으면 총괄이 사용자에게 확인 후 담당을 바꾼다.

## 6. 개선 루프

한 번의 기능 추가가 아니라 아래 주기를 반복한다. 주기 하나가 끝날 때마다 [loop-log.md](loop-log.md)에 한 줄을 남긴다.

```
 ① 검토 ─▶ ② 분류 ─▶ ③ 승인 ─▶ ④ 구현 ─▶ ⑤ 검증 ─▶ ⑥ 기록 ─┐
   ▲                                                       │
   └───────────────────────────────────────────────────────┘
```

1. **검토**: [검토 관점](review-lenses.md)별로 현재 앱을 평가해 `docs/reviews/<날짜>-<관점>.md`에 남긴다. 발견마다 근거(화면·코드 위치·자료 출처)와 심각도를 붙인다.
2. **분류**: 총괄이 발견을 과제 카드로 만든다. 같은 원인은 한 카드로 묶고, 카드마다 측정 가능한 완료 조건을 쓴다.
3. **승인**: 사용자가 이번 주기에 할 카드를 `ready`로 승인한다. P0는 총괄이 바로 `ready`로 올리고 사용자에게 알린다.
4. **구현** · 5. **검증**: 4장 순서대로.
6. **기록**: 무엇이 좋아졌는지(측정값·화면)와 다음 주기에서 다시 볼 것을 남긴다.

주기를 자동으로 돌리려면 총괄 에이전트에 정기 작업을 걸어 "보드 확인 → 막힌 카드·검증 대기 정리 → 다음 `ready` 카드 진행"을 반복하게 할 수 있다. 정기 실행은 사용자가 켤 때만 쓴다.

## 7. 다른 문서와의 관계

- [AGENTS.md](../../AGENTS.md): 변하지 않는 원칙. 모든 에이전트가 먼저 읽는다. `CLAUDE.md`와 `GEMINI.md`는 이 파일을 가리킨다.
- `docs/tasks/`: 과제별 현재 상태(유일한 진실 원천).
- [docs/handoff.md](../handoff.md): 저장소 전체의 최신 요약과 인계 패킷. 과제 상세는 카드로 연결만 한다.
- `docs/reviews/`, `docs/research/`: 검토·조사 결과 원문.
- [docs/validation.md](../validation.md): 릴리스 단위 검증 증빙.
