## Claude에게 복사할 프롬프트

```text
[GEMINI_DISPATCH → CLAUDE: 범용 업무 허브 기술 설계·개발 계획]

목표는 국립공원공단 직원이 사업·일반 업무·회의·자료·일정·보고·인계를 한곳에 축적하는 범용 데스크톱 앱이다. 전문 직무는 모듈로 확장하고, 내부 API가 준비되면 같은 업무 맥락에서 협업하도록 설계한다.

현재 앱은 달력·브리핑·인수인계/제출·메모·순찰·AX 사업·자료 보존 기능이 있다. 다음 도약은 ‘회의/전화 메모 → 후속 작업 → 사업·근거 자료 연결 → 기한 관리 → 완료 → 주간 실적·인계 초안’이다. 오늘의 업무 / 사업 공간 / 정리·보고 세 화면을 공통 경험으로 잡는다. 짧은 할 일은 사업 없이도 등록할 수 있어야 한다.

먼저 AGENTS.md, 최신 과제/인계, docs/product/direction-2026-10-20.md를 읽어라. 방향안은 origin/task/task-product-direction-01에 있다. 진행 중인 SECURITY 작업은 체크포인트로 보존하고 다른 카드/코드를 덮지 마라. Gemini는 별도로 직무 시나리오·화면을 설계하므로 그 응답을 기다리지 말고 아래 기술 산출물을 먼저 작성하라.

산출물:
1. 현재 구현과 목표 사이의 핵심 격차 5개 이하. 근거 파일을 붙일 것.
2. 범용 Project·WorkItem·회의/결정·ResourceLink의 최소 모델과 참조 관계. 기존 tasks·axProjects·patrols·암호 저장/백업과의 호환 경로를 포함할 것.
3. 모듈이 제공할 필드·보기·행동·보고 기여·버전 계약. AX와 순찰 두 사례로 코어 재사용을 설명할 것.
4. 위 핵심 흐름 하나가 끝까지 동작하는 첫 개발 묶음을 최대 3개 구현 카드 초안으로 나눌 것. 각 카드에 사용자 결과·범위·완료 조건·의존·검증 범위를 명시할 것.
5. 향후 기관 API 어댑터의 경계. 읽기 전용 연계, 사용자/권한, 공유 작업·댓글·동기화/충돌의 책임을 구분하고 미확인 API 계약은 가정으로 표시할 것.

이번 작업은 기술 설계와 개발 계획이다. 제품 코드·기존 스키마·보안 계약을 변경하거나 API에 접속하지 마라. 신규 구현 카드를 ready로 확정하거나 main에 병합하지 마라. 관련 공식 문서는 필요한 부분만 확인하고 전체 배경/CI 로그를 반복 복사하지 마라.

저장소 규칙에 맞는 문서 전용 과제/브랜치에서 docs/product/claude-architecture-response-2026-10-20.md에 기록하고 커밋·푸시하라. 문서 검사만 새 실행 결과로 기록하라. 응답은 결론·핵심 결정·쟁점·파일/실제 푸시 해시와 GEMINI_HANDOFF_PACKET으로 정리하라.
```

## Gemini에게 복사할 프롬프트

```text
[GEMINI_DISPATCH → GEMINI: 범용성 검증·제품 흐름·화면 설계]

목표는 국립공원공단 직원이 사업·일반 업무·회의·자료·일정·보고·인계를 한곳에 축적하는 범용 데스크톱 앱이다. 개인 단독 사용부터 유용하고, 직무 전문 기능을 모듈로 더하며, 향후 내부 API가 준비되면 협업으로 확장한다.

현재 앱에는 달력·브리핑·인수인계/제출·메모·순찰·AX 사업·자료 보존이 있다. 일반 사업/업무/회의/자료를 연결하는 흐름은 아직 부족하다. 사용자는 사업·업무·자료 연결, 반복 보고 시간 단축, 인계/공유 누락 방지를 모두 원한다.

핵심 흐름: ‘회의/전화 메모 → 후속 작업 → 사업·근거 자료 연결 → 기한 관리 → 완료 → 주간 실적·인계 초안’. 오늘의 업무 / 사업 공간 / 정리·보고 세 화면을 설계하라. 짧은 할 일은 사업 없이도 쓸 수 있어야 한다.

Claude는 병렬로 자료 모델·모듈 계약·개발 계획을 만든다. 그 응답을 기다리지 말고 사용자 경험 산출물을 작성하라. 코드/스키마 구현과 전체 제품 배경 재조사는 중복 수행하지 마라.

산출물:
1. 시설·자원보전·AX·행정 네 직무의 하루/한 주 시나리오를 각각 하나씩. 공통 흐름과 전문 모듈 차이를 구분하고 공식 절차가 아닌 내용은 가설로 표시할 것.
2. 위 세 화면의 텍스트 와이어프레임. 정보 위계·주 행동·화면 이동·빈 상태를 보여주고 핵심 흐름을 처음부터 끝까지 따라갈 수 있게 할 것.
3. 범용성 반례 최대 5개: 어떤 업무가 이 구조에 억지로 끼워지거나 빠지는가? 해결 방향도 붙일 것.
4. 첫 시제품에서 반드시 필요한 기능과 다음으로 미룰 기능. 사이드바/기능 수를 늘리는 것보다 중복 입력과 화면 왕복을 줄일 것.
5. 사용자 체감 수용 기준 5개 이하. 조작 수·중복 입력·자료 찾기·보고 근거를 측정할 방법을 제시할 것.
6. Claude/Codex가 결정해야 할 쟁점 최대 3개.

레퍼런스는 Notion의 사업/작업 연결과 다중 보기, Obsidian의 로컬 자료 연결, Microsoft Loop의 업무 맥락 협업을 우선 참고하라. 추가 조사가 필요하면 공식 문서 최대 3개만 활용하고 구체적인 상호작용과 적용 한계를 설명하라. 기관 메신저/AI/모든 모듈을 한 번에 구현하는 안은 피하라.

참고 방향안:
https://github.com/Recon987/AI-Coding/blob/d777483e3f48092ffc241588c076f90ad466d679/docs/product/direction-2026-10-20.md
문서에 접근할 수 없으면 위 공통 브리프를 기준으로 작성하고 확인한 사실과 가정을 나누어라. 연결된 디자인 도구가 있으면 시안을 활용하되, 없으면 텍스트 와이어프레임으로 완성하라. 도구를 사용하지 않았는데 사용했다고 말하지 마라.

응답은 ‘권고 방향 → 네 직무 비교표 → 세 화면 와이어프레임 → 우선 기능/수용 기준 → 쟁점’ 순서로 작성하라. 저장소 수정은 하지 말고 사용자가 Claude·Codex에 전달할 수 있도록 독립된 검토 결과로 제공하라.
```

## 병렬 작업 종료 후 합치는 방법

사용자가 두 응답을 Codex에 전달하면 동일한 결정표에 공통점·차이·근거·결정 주체를 정리한다. 공통 시나리오와 자료 계약을 먼저 고정하고, 첫 시제품 범위를 사용자와 확인한다. Claude의 구현 카드 초안에 Gemini 화면 동선/수용 기준을 반영한다. 아직 받지 않은 응답을 동의/승인으로 기록하지 않는다.
