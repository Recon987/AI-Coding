# 단계별 설계 제안

## 1. 개인용 로컬 업무 공간 (현재)

React + TypeScript 화면과 Electron 데스크톱 호스트를 사용한다. 화면에는 Node.js 권한을 주지 않고 제한된 preload IPC로 저장, 폴더 열기와 백업만 제공한다. 외부 페이지와 새 창 탐색을 막는다. 개인 PC용 JSON 저장부터 시작하며 여러 사용자의 동시 접근은 지원하지 않는다. 기능이 늘면 스키마 마이그레이션과 트랜잭션을 갖춘 SQLite로 전환한다. 정식 운영 전 Windows 서명·설치 검증, 암호화, 백업 보존 정책, 접근 제어와 감사 로그를 검토한다.

## 2. 법령 반입·검색

인터넷 수집기와 폐쇄망 서비스를 분리한다. 가능한 경우 국가법령정보센터 등 공식 제공 API와 이용 조건을 먼저 확인하고, HTML 파싱은 허용 범위와 구조 변경을 고려한 보조 수단으로 둔다. API 인증은 인터넷 구간 수집기에만 둔다.

인터넷 수집기는 법령 ID, 법령명, 공포일, 시행일, 조문 구조, 원문 출처, 수집 시각과 원문을 묶는다. 자연공원법을 시작점으로 산림·야생생물·안전·계약·회계 등 담당자가 검토한 목록을 관리한다. 특정 법령의 적용 여부를 앱이 자동 확정하지 않는다.

반입 패키지에는 버전, 파일별 SHA-256, 개정 이력, 디지털 서명을 포함한다. 해시만으로는 위조를 방지할 수 없으므로 폐쇄망에 배포한 신뢰 공개키로 서명을 검증한다. 기관 반입 절차와 악성코드 검사를 거친 뒤 서버의 반입 대기 폴더에서 검증 → 담당자 승인 → 임시 DB 적재 → 원자적 버전 전환 순서로 처리한다. 압축 해제 경로 이탈과 과도한 파일 크기를 차단하고 실패 시 이전 버전을 유지한다.

폐쇄망 서버는 전문 검색(SQLite FTS 또는 서버형 검색 DB), 조문별 개정 비교, 현행/시행 예정 구분을 제공한다. 앱은 폐쇄망 서버에만 접근한다. 마지막 성공 수집·반입 시각과 자료 기준일을 항상 보여 오래된 정보를 최신으로 오인하지 않게 한다. 원문과 출처를 보존하며 검색 결과는 법률 자문의 대체물이 아니다.

## 3. 사무소 공유 기능

서무·순찰·당직·민원은 사용자, 부서, 사무소 단위 권한과 이력·승인 모델을 정의한 뒤 서버 DB로 확장한다. 일정의 원본 업무 ID를 연결해 서류 제출 기한과 당직 변경이 알림으로 이어지게 한다. 예산·급량비 계산은 기관의 실제 규정과 검증 사례를 받아 설계한다.

ERP는 클라이언트가 DB 계정으로 직접 접속하지 않게 한다. 공식 조회 API 또는 DBA가 승인한 읽기 전용 뷰를 중계 서버에서 이용한다. 최소 필드, 인증 방식, 갱신 주기, 재직·휴가 정보 공개 범위, 장애 시 캐시 표시와 망 연계 정책을 협의해야 한다. 접근 확인 전 실제 연결이나 동기화를 구현하지 않는다.

## 4. 유틸리티 및 개인 영역

좌표 변환은 입력·출력 EPSG 코드, 축 순서, 단위와 검증 기준점을 명시한다. 파일명 변경은 미리보기, 충돌 검사, 적용 이력과 되돌리기를 먼저 만든다. 개인 경조사·용돈은 기관 업무 저장소와 분리하며 서버 동기화 기본 대상에서 제외한다. 문서 편집기는 자동 실행 플러그인 없이 기본 텍스트 편집부터 확장한다.

## 다음 결정 사항

공유 사용 인원과 서버 OS, 최초 도입할 업무, 자료 보안 등급, Windows 설치 권한, 배포·서명 정책, 알림의 종료 중 동작 요구, 법령 수집 API 사용 조건, ERP 제공 방식이 정해지면 후속 단계를 구체화한다. 이 항목들은 개인용 시제품 실행을 막지는 않지만 정식 배포 전에 결정해야 한다.
